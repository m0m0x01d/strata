      Payloads

      Lab notes

      STRATA turns a vulnerable app into a cross-section you fly through: seven planes stacked in depth, all rendering the same request at once. Four labs ship in this prototype — one SQL injection and three cross-site scripting — chosen so the same instrument teaches four different bug classes without changing its rules.

      The one rule that makes it teach

      Every byte that originated from the student is drawn in amber, at every layer, without exception. Nothing else in the interface is warm. You track your own payload from keystroke to query string to parser to DOM without being told where to look — and the moment amber stops being data and becomes syntax (SQL) or markup (HTML) is visible, not narrated.

      Taint
      User-controlled bytes. The only warm hue in the system.
      Signal
      The instrument itself — chrome, labels, keywords.
      Breach
      A boundary crossed, a parser broken, a request blocked.
      Safe
      Data that stayed data. The baseline you’re breaking.

      Each lab has a different taint signature

      The reason the same seven planes teach four bugs is that the payload takes a different path through them each time. Fly to cross-section view (⌥space) and the shape is legible at a glance:

      • Lab 01 · SQL injection — taint present at every layer; it crosses the trust boundary at the server’s f-string and is promoted from string data to SQL syntax at the parser. A hand-written lexer computes quote balance and comment position, so a lone ' produces a real unterminated-literal error at a real offset.
      • Lab 02 · Reflected XSS — taint present at every layer; the server reflects it unescaped into the response, and the HTML tokenizer promotes it from text to markup. Because it is parsed at page load, even a bare <script> runs.
      • Lab 03 · DOM XSS — taint tunnels through the client and skips the network entirely. The payload lives in the URL fragment, which browsers never send, so the request, edge, and server planes go dark — the bug is a source→sink flow in client JS. And <script> written via innerHTML is built but never runs; you need a self-firing handler.
      • Lab 04 · Reflected XSS + WAF — taint is stopped at the edge unless you slip past it. The filter is a blocklist, and the lesson is that its grammar (string matching) and the browser’s grammar (HTML tokenizing) disagree — <svg onload> is not on the list, and no finite list covers every tag and handler.

      The engine is honest

      Under the surface, each lab runs a real analysis, not a lookup table. The XSS engine tokenizes the payload, classifies each vector by whether it auto-fires in the current rendering mode (a <script> that runs when server-reflected but not when set via innerHTML; a javascript: href that needs a click but an iframe src that doesn’t), and the resulting DOM tree on L6 is built by the browser’s own parser reading your bytes. The WAF scans your raw input against real regexes and highlights the matched token. Nothing actually executes — the alert() on the surface is a simulated dialog once the engine has proven the vector would fire. Same philosophy as the SQL lexer: real reasoning, simulated effect.

      What a production build needs next

      A sandboxed backend per lab so payloads aren’t enumerated and students can free-type real exploits; a lab-manifest format so labs are authored as data files rather than code (the five here already share one lab interface — analyze, layerState, render, solved — which is the seam that format would formalize); per-layer defense annotations that light up green when a student patches the right plane (parameterize the query, autoescape the template, write to textContent, add an allowlist); and saved progress. The layer engine, the taint renderer, and the cross-section are the reusable core — everything else is lab content.
